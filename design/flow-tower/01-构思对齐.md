# 流动塔插件 · 构思对齐（讨论层）

> 配套 `00-精读笔记.md`（事实层）。**本文件里除引用外全部是待确认的解读与判断，不是已验证结论。**
> 状态：第 0 轮，等用户校准。命名 "SDH" 与 "DSH" 是否同指 DeepSeek Harness 待确认。

---

## 1. 我对构思的复述（请校准）

> 每一座塔是一套"叶层原文 → 逐层摘要 → 塔尖"的金字塔；塔不是静态的，会随对话推进而流动变化；塔尖之外还有一层"分总层"，做多座塔之上的大概括，并能管理这些塔。

如果理解对了，这个构思最值钱的地方在于：**现有资料里，"塔内怎么建"已经很成熟，但"多座塔之上那一层"几乎是空白**（见 `00-精读笔记.md` 第 6 节）。所以真正要设计的不是树，是**跨塔层**。

---

## 2. "流动"至少有三种意思，需要选

| 编号 | 含义 | 对应已验证原型 | 代价 |
| --- | --- | --- | --- |
| F1 | **节点向上流动**：新叶进来，攒够阈值合并成父节点，逐层上浮 | bgx666 的 `mergeUp`（9/3/8）、MemGPT 的压力驱逐 | 最成熟，但方向单一、只增不减 |
| F2 | **塔形自适应**：层数/分叉由内容决定，节点可下沉、可重挂、可剪枝，深度随相似度阈值变化 | MemTree `θ(d)=θ0e^(λd)`（θ0 0.8→0.1 让树从 1–2 层变到 8–14 层）、HiRAG `CS_i` 动态定层、HTM M4 演化重写 | 最贴合"流动"，但**会让前缀缓存失效**，且遗忘策略学界还没定论 |
| F3 | **塔与塔之间流动**：内容从一座塔迁到另一座、两塔合并/分裂、热塔冷塔迁移 | qinghuaju `hot/warm/cold` + `space.mjs` 的 project/global 空间、MemOS Multi-Cube 动态组合 | 最贴"管理多座塔"，但资料里**没有现成实现**，连 ID 命名空间都得自己定 |

我的倾向：**F1 是地基、F2 是"流动"这个名字的真正含义、F3 是分总层的职责**。三者可以叠加，但第一版只做 F1 + 少量 F2，别一上来就 F3 全量。

---

## 3. "塔尖外的分总层"有两种读法，差别很大

- **读法 A（跨塔元层）**：塔尖之上再一层"总概括"，它不存细节，只存**每座塔的一句话画像 + 塔 ID + 时间范围 + 主题向量**，查询时先命中塔、再进塔内下钻。作用 = 路由器 + 预算控制器。
- **读法 B（分述—总述结构）**："分总"指中文写作里的先分后总，即每个父节点都由"分述若干条 + 一句总括"组成，塔尖外那层是把所有塔的分述汇总成一份全局总述，偏向**报告/视图**而非检索入口。

也可能 A 和 B 都要：A 管路由，B 管人看。但两者的写入时机、失效策略、token 预算完全不同，**得先定主职责**。

⚠️ 一个必须正面回答的反证：APDMem 自承 `retrieval recall depends on the quality of the L0 thematic summaries`，且 `does not explicitly model cross-session relationships`；《Harness the Memory》给出 `retrieving more entries helps QA but hurts agentic decisions`。所以如果分总层只是"把各塔摘要再摘要一遍"，它同时踩中**单点漏召回**和**宽召回伤决策**两个坑。
我的倾向：**分总层不要当"更大的摘要"，当"带预算的路由器"**——常驻上下文只放塔 ID + 一句话画像 + 代价估计，绝不把多塔摘要全量塞进 prompt。

## 4. 一个最小可行骨架（推测，待用户校准后细化）

```
[ 常驻上下文 ]  分总层：tower_id | 一句话画像 | 时间范围 | 活跃度 | 预估下钻代价   ← 极窄，前缀稳定
        │  路由（按查询选 1~2 座塔，其余不进上下文）
        ▼
[ 塔内 ]  L0 摘要根 → L1 主题节点 → … → Ln 叶层原文（details / 文件句柄 / 行号）
        ▲  按需下钻，够用即停
[ 流动 ]  新消息 → 叶 → 满阈值合并上浮 → 父重摘要；可选：相似度阈值触发重挂/剪枝
[ 原文 ]  append-only，永不被摘要覆盖；节点只存 ID 与范围映射
[ 存储 ]  tower_id + session_id 复合分区（bgx666 目前只有 session_id，必须改）
```

可直接抄的零件（出处见精读笔记第 5 节）：PageIndex 的 ID↔范围双向映射、graphiti 的双时态软失效与 `search_(group_ids=[...])`、claude-mem 的三步渐进检索、langmem 的 tool_call 配对保护、bgx666 的 `details` 原文保真 + `is_active=0` 可回溯合并 + run 事务回滚。

## 5. 五个必须先定的决策点

1. **塔的边界是什么**：一次会话一塔？一个项目/主题一塔？还是按时间窗切塔？——决定 `tower_id` 怎么生成、以及"什么时候该新建一座塔"。资料里 `session_id` / `thread_id` / `group_id` / `cube_id` / `project` 各是一套，没有共识。
2. **流动由谁触发**：固定阈值（bgx666 的 9/3/8）？相似度自适应（MemTree θ(d)）？token 压力（MemGPT 70%/100%）？还是模型自己决定（APDMem controller）？——直接决定缓存失效率与延迟。
3. **分总层是否参与生成**：只做索引/路由（进 prompt 的是塔 ID），还是也产出一段"全局总述"塞进上下文？——前者安全，后者踩宽召回坑。
4. **原文层放哪**：SQLite `details`（bgx666）、Markdown 文件（EverOS/basic-memory）、还是外部结果文件 + 引用（与你平台双库约束最合）。
5. **"分总层"要不要可逆/可审计**：要不要像 qinghuaju 那样有 `audit` 表、像 LangGraph 那样能回到压缩前的检查点？——决定它是"视图"还是"状态机"。

## 7. 我的初步判断（观点，非事实）

1. 别从"做一棵更好的树"入手——树这一层 RAPTOR/MemTree/bgx666 已经把路走完了，差距只在**动态重组**。
2. 真正的新东西是**跨塔层**，而它最大的风险不是"概括不够全"，是"概括太全导致注意力被拉走"。设计目标应该是**少召回、准路由、可回溯**。
3. "流动"最好理解成**塔形随内容自适应 + 层间可升降**，而不是单纯的时间推移；但每动一次塔形就要付一次缓存代价，得给流动设一个**静默期/批量窗口**（这点在资料里没人明说，是我的推断）。
4. 第一版建议把分总层做成**只读索引 + 显式路由工具**，先别让它自动改写塔内内容——APDMem 的 L0 教训说明，元层一旦写坏，下面全塔失联。

## 8. 第 1 轮用户校准结果（2026-11-11）

用户回答：

1. **"流动"四种全选**，并补充：「严格来说咱们应该是流动树」。→ 采纳命名修正：**塔是外形比喻，树是数据结构**；内部结构称"流动树"，"多座塔"理解为多棵流动树共存。
2. **分总层"两者都要"**：既做检索路由，也产出全局总述。
3. **宿主确认为 DeepSeek Harness 插件**：沿用 `dsh.bundle.patch` + prototype wrapper 挂载方式。

### 8.1 四种流动的正交模型（本轮新增判断）

| 编号 | 维度 | 发生位置 | 触发 | 归属调度器 | 主要代价 |
| --- | --- | --- | --- | --- | --- |
| ① | 垂直上浮 | 树内层级 | 固定阈值（9/3/8） | 压缩事务 | 需 run/rollback 保 tool_call 配对 |
| ② | 结构自适应 | 树内拓扑 | 相似度 `θ(d)` | 重排调度器 | **前缀缓存失效**，需静默期/批量窗口 |
| ③ | 时间冷热 | 树内元数据 | 时间窗 | 元数据任务 | 只改 tier，不动结构，最廉价 |
| ④ | 跨树迁移 | 树间 | 分总层决策 | 分总层 | 跨 `tower_id` 命名空间，需 ID 全局唯一 |

**判断**：四类不能塞进同一调度器。触发条件、锁粒度、事务边界、缓存影响完全不同；混在一起最可能的失败是"压缩事务回滚时连带回滚跨树迁移"或"一次重挂打散整段前缀缓存"。建议拆成四类事件 + 一条"结构变更静默期"规则（此规则为**推断**，资料里没人明说）。

### 8.2 分总层双视图的硬规矩

- **路由视图**：常驻上下文、极窄（tower_id + 一句话画像 + 时间范围 + 活跃度 + 下钻代价）、低频写、前缀稳定；只在树的新建/合并/归档时变更。
- **总述视图**：按需生成、带版本号与时间戳、可失效重算、不常驻；主要给人看或作低频背景。
- **硬规矩：总述视图不得回写影响路由决策。** 否则形成 `总述写坏 → 路由选错树 → 取回更偏的材料 → 总述更坏` 的闭环，正是 APDMem L0 单点故障的放大版。

### 8.3 DSH 宿主：做"多树"必须改的 5 处硬编码（bgx666 版实测）

1. `index.js:166` `let active = null` 全局单实例持有 prototype hook，多实例互相顶掉；而 prototype 钩子本身只能有一个 owner → 需改成按 tower 索引的注册表 + 单入口分发。
2. `store.js` 单库单表 `PRIMARY KEY(session_id,id)`，`session_id` 是唯一分区键；`roots/stats/node/children/activeAtLevel/nextNodeId` 全按单 session → 需 `tower_id` 复合主键或每树一库。`runs/keeps/session_prefs` 同理。
3. `MEMORY_TREE_PROMPT`（`index.js:52`）写死「本会话维护**一棵**分层记忆树」；`renderNodeBlocks`（`text.js:205`）只渲染一棵树的 `roots`；`client.js` 的 `node(\d+)_(\d+)` 正则只解析 level+serial，无树前缀。
4. `explore_memory_tree`（`tool.js`）参数只有 `node_id`，无 tower；4 个 HTTP 路由按 `session`+`id`；`_jobs/_last/_keeps/_agents/_engines/_store` 全是 `Map` 以 `sessionId` 为键。→ 工具需加 `tower_id`（或 `tree_id`）并做跨树下钻。
5. `moveSession`（`store.js:515`）是**单树整棵迁移**且拒绝覆盖已有 target（Planner transfer 语义），不是多树共存；`client.js` 注释 "the tree is one evolving structure"，只渲染 `summaryEventSeq` 最大的一张卡。

**含义**：多树不是"加一个 tower_id 字段"就行，prototype 单 owner、prompt 单树、UI 单卡这三处是架构级改动。

### 8.4 下一轮待定（别一次定完）

- **树的边界**：一次会话一树 / 一个项目一树 / 主题聚类自动分树 / 时间窗切树？决定 `tower_id` 生成规则与"何时新建一棵树"。资料里 `session_id`、`thread_id`、`group_id`、`cube_id`、`project` 各是一套，无共识。
- 第一版是否就带 ④ 跨树迁移（我的建议：先只做"分总层能选树"，迁移放第二版）。
- 总述视图是否进系统提示词常驻（我的建议：不常驻）。
- `tower_id` / `tree_id` 命名统一，以及节点 ID 是否要带树前缀（涉及 `client.js` 正则与 checkpoint 兼容）。
