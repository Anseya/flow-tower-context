## 1 能不能让宿主的 LLM 完成语义抽取？

**能——宿主的 `llm` Service 可被插件直接调用**（本轮用 `cordis_inspect` 查到的精确契约）：

```js
const llm = ctx.get('llm')            // optional service，需判空；也可 inject ['llm'] 硬依赖
const model = ctx.get('agentDefaultModel')?.currentSelection() // 默认 provider/model
for await (const chunk of llm.stream({
  provider, model,                    // 必填路由
  system: 'Return JSON only.',
  messages: [{ role: 'user', content: [{ type: 'text', text: prompt }] }],
  maxTokens: 1000,
  sessionId, purpose: 'flow-tower-compile',
  signal,                             // 可取消
})) { if (chunk.type === 'text-delta') text += chunk.text }
```

- `llm.listProviders()` / `listModels(provider)` 可发现路由；`agentDefaultModel.currentSelection()` 可拿默认模型；
- 因此**主题/人物/关系抽取、摘要生成**都可以由宿主 LLM 在压缩后异步完成；
- **但 `llm` Service 只有 chat streaming，没有 embedding 接口**：神经向量检索不能靠“宿主 LLM”完成（除非 provider 另行暴露 embedding 路由）。因此“语义检索”仍是 BM25 + 稀疏向量/共现扩展。

**正确接法（建议，尚未实现）**：`llmCompiler: 'off' | 'shadow' | 'on'`，每次压缩最多 1 次调用、输出 ≤1000 tok；`shadow` 只写审计与 staging，不提交；`on` 需通过现有 proposal validator（JSON schema + citation seq 存在性 + 预算）才入库；失败回退确定性抽取。外部 `tools/propose-agent.mjs` 已经是同一管线的“外置生成器”，宿主接法只是把外部 HTTP 换成 `llm.stream`。

**风险**：成本/延迟（每次压缩一次调用）、prompt 注入（记忆内容不可信，LLM 输出也必须校验）、模型稳定性。所以默认必须 `off/shadow`，且不影响确定性路径。

## 2 递归摘要树：具体差在哪里

我们现在的“摘要树”= `summary_nodes`：卷 → 类别（code/memory/narrative/diagnostics）→ kind/module 组 → 词条；摘要是**确定性 top headwords 拼接**，每次编译整树重建。

与 RAPTOR / MemTree 的差距有六点：

| # | 差距 | 我们 | 对手 |
| --- | --- | --- | --- |
| 1 | **语义聚类** | 按 kind/module 固定分类 | 按 embedding 聚类（RAPTOR 递归 GMM，MemTree 阈值合并/分裂） |
| 2 | **抽象式摘要** | 词头列表（非句子） | LLM 生成段落摘要 |
| 3 | **动态深度** | 固定 3 层 | 深度随内容自适应（RAPTOR 递归、MemTree 在线插入） |
| 4 | **内部节点检索** | 只在词条层检索/遍历 | “collapsed tree” 对摘要节点直接向量检索，再下钻 |
| 5 | **增量更新** | 每轮整树重建（O(n)） | 节点级插入/更新/重挂 |
| 6 | **摘要可信度** | 无（只是词头） | 摘要可少而精，能作为答案素材 |

**低成本改进路径**（不需要 LLM）：
- 用 citations 的原文做**抽取式摘要**（组内最高频句/首句），替代纯词头；
- 在 `search_terms` 里索引 summary 文本，支持“先搜摘要、再下钻词条”（补第 4 点，不需要嵌入）；
- 组摘要只在组内容变化时重建（目前整树重建，可优化，见 §5）。
- LLM 摘要等 §1 接好后作为 `summaryGenerator`。

## 4 多实例并发：是不是大问题？

**是真问题，但对我们这个单机桌面插件，风险可控且已明显收窄**：

| 层面 | 措施（v0.15） |
| --- | --- |
| 编译写入 | 每个项目 DB 一把跨进程 `.write.lock`（读/采样在锁外，写入阶段串行）；拿不到锁就跳过本轮并告警，不写坏 |
| 关系同步 | `.relations.lock`（已有，v0.12） |
| 跨塔合并 | `.merge.lock`（已有） |
| SQLite | WAL + busy_timeout=5s + `BEGIN IMMEDIATE` + busy 重试 |
| 读取 | WAL 并发读，不受锁影响 |

**仍不提供**：多主冲突合并、同一词条并发写合并、跨机同步。两个实例同时写同一项目可能“后写覆盖前写”（幂等、不损坏），编译可能被跳过一轮（下次压缩会补）。**建议**：一个项目同一时间只跑一个 DSH 实例；若必须多开，不同项目互不影响。

### 5.2 长会话模拟（新增 `eval/long-session-eval.mjs`）

把当前真实 session（**5017 事件 / 1686 消息**）按累积窗口切成 8 轮压缩 + 1 轮重复压缩：

| 指标 | 结果 |
| --- | --- |

| 最终词条 | 2080（8 轮） |

| digest | 332–396 tok（≤400 预算） |
| 重复轮 | 0 新增（幂等），约 0.5s（含 GC） |
| 引文保真 | 100% |
| 库大小 | 15.5MB（含搜索索引/引用/关系） |
| 总耗时 | 7.9s（8 轮） |

### 5.3 本轮做的优化

1. **空轮/仅摘要变化不重建**：只有 `created+updated+citations>0` 才 bump version 并重建组/摘要/关系（之前 abstract 变化也会整树重建）；
2. **关系同步从按“时间水位”改为按“本轮变更 entryIds”**：修复了事件时间与轮次时间不同导致的漏边（关系从 7042 补到 13307），且只处理变更条目；
3. **层级关系边按组签名重建**：组结构不变时不重写 entry→group→category→volume 边；
4. **编译写入加跨进程写锁**：多实例不并发写坏；
5. 前后对比：同一模拟 8 轮 **8.4s → 7.9s**；关系完整性从“漏 900 条”到全量；重复轮 0 写入。

### 5.4 仍需补的验证

- **多会话纵向统计**：目前只有 1 个真实压缩 + 1 条模拟长会话；需要多开几个真实项目会话，统计压缩次数、注入次数、缓存命中、词条增长曲线；
- **digest 注入上限**：目前每卷 ≤40 次，真实长会话可能触顶（本会话仅 2 次）；
- **真实多实例**：未在双进程下实测（只有锁单测）。

## 6 结论

- 宿主 LLM：**可接**（`ctx.get('llm').stream` + 默认模型），主题/关系/摘要都能做；embedding 不在该服务内，语义检索仍需词法/稀疏向量。
- 摘要树：差在“语义聚类 + 抽象摘要 + 递归深度 + 摘要层检索 + 增量更新”，可先做抽取式摘要与摘要索引（无需 LLM）。
- UI：不扩，保持只读简单面板。
- 并发：已用“锁 + 串行写入 + 幂等”收窄；不承诺多主。
- E2E：已用真实日志做 8 轮模拟并修复两项实质问题；下一步是多真实会话统计。

## 8 能力预估（编程任务 vs 长文本小说）

> 数据来源：本仓 `eval/offline-eval`、`eval/real-session-eval`、`eval/txt-corpus-eval`（代码语料 12 文件 / 21 万字符；小说全本 8.4M 字符）、`eval/long-session-eval`（1686 消息/8 轮）、`eval/relations-bench`。

### 8.1 编程任务

| 维度 | 实测/预估 | 结论 |
| --- | --- | --- |
| 代码语料抽取密度 | 212KB 源码 → 154 词条（**7.25/10KB**）；file 34 / feature 35 / api-symbol 33 / decision 18 / error 13 / topic 21 | 文件/符号/错误/任务抽取可用；函数级语义弱 |
| 编译成本 | 21 万字符 352ms；真实会话 414 词条；长会话 8 轮 0.58–1.68s/轮 | 实时可接受 |
| 检索 | BM25 + 稀疏向量/共现；lookup/cite 保真 100% | "记得大概/文件/错误/任务"可查；"按语义找代码"弱 |
| 关系图 | 真实库 8257 边（parent/derivedFrom/relatedTo），十万边基准 PASS | 可追踪"改了什么/由什么派生/属于哪个模块" |
| 典型强项 | 项目/模块/任务/错误/决定/文件/符号的索引与时间线；压缩后细节不丢 | 适合"项目记忆/交接/回溯" |
| 典型弱项 | 无 AST/调用图、无函数级摘要、无代码 embedding；大仓库只能靠 module 前缀粗分 | 不适合替代代码检索/理解工具 |

**预估结论**：编程任务上，它是"长期项目记忆 + 可回溯索引"的强项工具（8/10），不是代码智能（语义/调用图）工具（4/10）。最适合：跨压缩的决策/任务/错误追溯、文件与模块时间线、任务闭环、关系溯源。

### 8.2 长文本小说

| 维度 | 实测/预估 | 结论 |
| --- | --- | --- |
| 规模 | 全本 **8.44M 字符** → 2846 词条（chapter 2531 / person 160 / decision 112 / topic 24），编译 5.5–7s，库 13–15MB | 单卷可承载全本；远超"1.2MB 天花板"旧结论 |
| 抽取 | 章节 2531（≈全书章节）、人物 160（对白署名+频次）；叙事模式抑制"决定/任务"误判 | 结构/人物可信；情节关系弱 |
| 检索 | 查询/引文保真 **100%**；按章节/人物/时间可查 | "哪一章/谁/什么时候"可查 |
| 关系 | parent（章节/模块层级）+ relatedTo（弱共现），无人物关系/情节图 | 无知识图谱级人物关系 |
| 摘要 | 抽取式组摘要（citation 原文摘句）+ 摘要检索 | 能给出"这组大概讲什么"，非抽象情节摘要 |
| 典型弱项 | 情节因果/人物关系/主题语义、跨章推理 | 不适合当"小说问答/推理" |

**预估结论**：长文本小说上，它是"章节/人物/时间线/原文定位"的强索引（7.5/10），不是情节理解或人物关系推理（4/10）。最适合：小说资料管理、章节定位、人物出场检索、超长文本不丢原文。

### 8.3 共同边界（预估）

- 单卷 4000 词条 + 滚动淘汰；超长内容会淘汰冷门条目（任务/决定/章节保护）；
- digest 每轮 ≤400 tok、每卷 ≤40 次注入；超长会话注入会封顶；
- 语义靠词法/共现，跨语言/同义仍弱；LLM 影子可补语义但默认关闭；
- 多实例只保证不并发写坏，不保证多主合并。
