## 1. 项目全貌

### 1.1 定位（一句话）

给 DSH 一个**自动、项目本地、原文可回溯**的长期上下文记忆层：压缩发生时把被遮蔽的对话增量编译成六维词典（项目/模块/功能/任务/时间 + 叙事），下一步以受预算约束的 digest / Project map 注入，模型再通过 6 个 `dict_*` 工具按需下钻并用 `seq` 引文逐字回放原文。

**它不解决**：通用聊天记忆、跨应用个人助理、知识库 RAG、多 agent 调度、语义问答基准。

### 1.2 架构与数据流

```
DSH 会话 ──(compaction/start|summary 事件)──▶ 主插件观察者
                                              │
                    ┌─────────────────────────┴──────────────────────┐
                    ▼                                                ▼
          确定性编译器 extract/relations                      digest 注入层
          （file/feature/decision/task/                    systemPrompt legend
            command/error/topic/chapter/person）             + agent/pre-step digest
                    │                                         + adaptive budget
                    ▼                                                │
        <项目>/.flow-tower/flow_tower.db  ◀── dict_* 工具 / 面板 / MCP ──┘
        （entries/citations/groups/summary_nodes/relations/metrics/kv）
```

- **接入方式**：Host 平面 bundle（`@local/flow-tower`）+ 自带 `compaction/index.js` provider；不 import `@deepseek-ai/*` 包，靠 asar 绝对 URL 取 `BasicCompactionEngine`。
- **编译触发**：`session/event` 的 `compaction/summary`（权威增量是 `shadowedSeqs`），可审计、幂等、失败回退。
- **注入**：稳定 `systemPrompt` 段（legend + 检索协议）+ 每步首条 digest（`on-change`、版本门控、每卷 ≤40 次）；大项目（词条 ≥200）自动切 Project map。
- **访问**：`dict_browse / dict_lookup / dict_cite / dict_timeline / dict_search / dict_relate`，面板（Tree/Timeline/Tasks/Graph/Settings），只读 HTTP API，stdio MCP server。
- **治理**：模块契约块 + `tools/module-graph.mjs --check`（缺失契约/依赖漂移/循环）+ LOC 门禁（400 警告 / 700 失败 + exemptions）。当前 67 模块 / 0 循环 / 4 警告 / 2 例外。

### 1.4 本轮 `/compact` 的证据（修正前；修正后见 §1.4.2）

**已闭环的部分（B 级）**：
- `.flow-tower/compaction-runs.jsonl` 出现 `source:"event"` 行：`backend:"FlowTowerCompactionEngine"`, `ok:true`, `ms:25379`, `summaryChars:13170`, `compactedSeqs:661`；
- 压缩后 DB 词条 +220、关系 +1745，说明"压缩→自动编纂"链路真实工作；
- 压缩后注入计数 +1，说明 digest 在压缩后的首步重新注入。

**必须修正的部分（A 级）**：本轮压缩**不是** FlowTower 的 `summarize()` 执行的。
- 证据 1：`flow-tower-compaction` 的 `summarize()` 一旦执行，必然写 `C:\Users\wuhao\.dsh\flow-tower\compaction-engine-debug.log` 和一条带 `memoryChars` 的 run-log 行；两者都不存在（全盘搜索也只有一个 run-log 文件）。
- 证据 2：`/api/status.compactionDiagnostics.summarizeHasFlowMemory=false`。
- 证据 3（根因）：当前会话使用的 `cordis` 预设在自己的 isolate 组里挂了一份 `compaction-basic`：
  `dsh-web-app/presets/cordis.patch.yml:68-84` 的 `compaction` 组声明 `isolate: {compaction:true, toolResultPruner:true}`，组内是 `@deepseek-ai/dsh-compaction-basic`。Host 平面的补丁（disable `compaction-basic`、insert `./compaction/index.js`）**只影响 host 平面**，不进入 preset 的 isolate 组。
- 证据 4：`cordis_inspect_query(Config)` 在 host 平面只能看到 `include:compaction-basic`（inactive）与 `include:flow-tower`（absent），看不到 preset 内部条目；`/api/status.compactionBackend` 读的是 host 平面的 `ctx.get('compaction')`，因此**状态字段会误报**。

**结论**：目前 FlowTower 实际提供的是"观察 + 编纂 + digest 注入 + 工具"；压缩摘要里的项目记忆注入没有生效。要让"真实的 DSH 压缩路径"成立，必须在 **preset 层**（`preset-cordis` 的 `config.plugins` 的 `compaction` 组）把 `compaction-basic` 换成 `./compaction/index.js`，而不是在 host 平面插入。

**B 方案（2026-11-15 已写入 profile，重启后三证据验证通过）**：
- 在 profile `cordis.patch.yml` 末尾新增 `- id: preset-cordis` 覆盖，`config` 全量重述（Loader 对 config 是整体替换，不能深合并）；
- `compaction` isolate 组内 `compaction-basic` 的 name 改为字面量 `file:///E:/dsh-plugins/flow-tower/compaction/index.js`（不依赖 profile/asar 的包解析）；
- 同步把 `skill-filesystem` 的 `baseUrl` 表达式替换为 asar 绝对路径，避免行被覆盖后解析基址变化；
- 已用 Loader 的 `applyEntryPatches` 离线仿真：`preset-cordis` → `compaction` 组 3 行，`compaction-basic` 指向 Flow Tower 文件，23 个插件行齐全；
- 重启后三证据验收通过（见 §1.4.2）；风险与回退见 `22` §6。

## 2. 对比框架

旧文档用"1–5 分加权总分"（09/12/17），问题是权重主观、把不同生态的方案放在同一把尺子上。本文改为**三判据 + 七维度**，只给相对结论，不给总分。

### 2.1 三条硬判据（先过门槛）

1. **事实源**：方案的事实源是什么？（原文日志 / 改写事实 / 模型内激活 / 无）可回溯到什么粒度？
2. **宿主关系**：是宿主内接缝（插件/压缩引擎/工具），还是外部服务/框架？谁拥有上下文装配权？
3. **常驻成本**：每步注入多少 token？构建/查询各花多少 LLM 调用与延迟？成本落在写侧还是读侧？

### 2.2 七个维度

| 维度 | 说明 |
| --- | --- |
| 写入路径 | 压缩事件驱动 / 逐工具捕获 / LLM 抽取 / 人工 |
| 结构与存储 | 平铺 / 树 / 图 / 文件系统 / OS 分页 / 模型内 |
| 检索 | 词法 / 向量 / 图遍历 / LLM 导航 / 混合 |
| 证据与溯源 | 无 / 事实+来源 / 句柄 / 逐字原文 |
| 注入策略 | 预注入（常驻）/ 按需 JIT / 折叠对象 / 不注入 |
| 成本形态 | 写放大 / 读放大 / 构建一次性 / 常驻 token |
| 运维与集成 | 零依赖 / 服务化 / 数据库 / 训练依赖 |

| HiRAG | 层次 KG + 摘要实体 + 桥接（关键实体最短路） | 桥层是原文三元组（中） | 索引成本≈GraphRAG 2.5× | 中-高 | 借"桥接最短路"（纯图算法）；反模式：GMM/embedding 分层+逐层摘要 |

| GameAgentSurvey | 记忆结构综述（chunks/KV/树/图/参数化） | 综述不评估 | — | 中 | 借分类框架；"遗忘/合并"仍是开放问题 |

### 3.2 八条硬结论（合并 design/02 的 15 条与本轮精读）

1. **"原文叶"是少数派**：RAPTOR、ReadAgent、APDMem L3、HORMA note、CarryOn carriers 才有真溯源；GraphRAG/HiRAG 的叶是实体/关系/claim，无原文段。→ 我们的 `seq` 引文方向正确，且比多数研究方案更彻底。
2. **分层不是越多越好，必须保留"压平检索"旁路**：GraphRAG C0–C3 层间无统计显著差异；ReadAgent 附录 H 复现 MemWalker 树搜索 66.73% vs 全文 85.83%；MemTree 消融 k=10 与 collapsed 相当、k≤5 才掉分。→ digest 的"平铺 + token 截断"不是妥协，是必要形态；Project map 必须能一键退回平铺。
3. **原文层是精度来源**：APDMem 去掉 `read_raw` 掉 5.9%（最大单项），去掉 L2 只掉 0.5%。→ 我们的 `dict_cite` 不应只是"防幻觉备份"，应被 prompt 协议鼓励直达。
4. **写放大是树的真正代价**：离线聚类单条新增≈3753 次调用；在线树 3.27 次/插入且父节点反复改写；ConvMem 把成本挪到查询（5× 重扫）。→ 结构变更只能进压缩事务/静默期；我们的"压缩时增量编译"是正确取舍。
5. **父节点必须写侧硬预算**：MemTree 节点文本随深度膨胀（depth 10+ 中位约 800 tok）。→ 词条 gloss、摘要节点、digest 都必须写侧 clamp（我们已有 `glossTokens/nodeBudgetTokens/digestBudgetTokens`）。
6. **总述必须带句柄**：GraphRAG report schema 用 `[Data: Entities(5), Relationships(37)]` 防"总述写坏导致全塔失联"。→ Project map 每行带 `cite/rels` 是对的，还应带完成度证据。
7. **路由增益天花板不高**：HTM per-substrate 路由 0.671 vs 固定最优 0.648（+0.023）；oracle 0.93，提升在"问题级选择"而非"树级选择"。→ 不要做"多塔路由 agent"当卖点；先把单塔内的 map/lookup 做好。
8. **检索宽度按 regime 双档**：HTM 上 QA 类 k=5–20 更好、agentic 类 k=1–5 更大反而掉约 7 点。→ 工具默认小步（k=1–2、≤1000 tok/次），需要时显式放宽。

### 3.3 论文 → Flow Tower 机制映射

| 论文概念 | 我们的对应 | 状态 |
| --- | --- | --- |
| APDMem L0 摘要 / L1 事实 / L3 原文 | digest/Project map / 词条 / `dict_cite` | 已实现，成本阶梯可再显式化 |
| ReadAgent 页句柄 | `citation = session_id + seq 区间` | 已实现，且可跨会话 |
| HORMA note 指针 | 词条 gloss + citation | 已实现（gloss 短、不存原文） |
| RAPTOR collapsed | brief 平铺 digest / 摘要检索 | 已实现（非递归） |
| HiRAG 桥接 | `relations` 图 + `dict_relate` | 只差"最短路桥接" |
| GraphRAG 总述句柄 | Project map 行内 `cite/rels` | 已实现 |
| CarryOn execution context | digest 的 Goal/Open/Latest | 缺 current focus / next step |
| CarryOn validated fold | staging/validate/commit 提案管线 | 已具备确定性校验，缺语义校验 |

### 3.4 论文给我们的三条真实增量（按 ROI）

1. **桥接路径（HiRAG bridge，零 LLM）**：在现有 `relations` 图上做"两个命中词条之间的最短路/共同邻居"，把 `dict_relate` 从"列边"升级为"给一条证据链"。纯 SQL/图算法，无 embedding、无 LLM。
2. **execution context 最小集（CarryOn）**：digest 增加 `current focus` 与 `next step`（可由现有 open task + 最近 decision 确定性生成），解决"知道进度但不知道下一步"。
3. **预算二分（aider → Project map）**：不再"取前 10 模块再截断"，改为"按关系图排序 + 对选中行数二分直到命中预算 ±15%"，避免超预算时丢高价值项。

**明确不借**：MemWalker 多轮 LLM 导航、HORMA GRPO 检索器、ConvMem 每查询重扫、RAPTOR 离线递归重建、任何需要微调/embedding 的基质。

## 4. DSH 原生对比

> 依据：安装版 dsh 0.2.2-rc.3 的 `src/`（`@deepseek-ai/dsh-compaction-basic`、`dsh-compaction`、`dsh-token-meter`、`dsh-compaction-tool-result-pruner`、`dsh-command-compact`、`dsh-session`、`dsh-agent-loop`、`dsh-web-app/presets/cordis.patch.yml`）+ `cordis_inspect_query`。

### 4.1 原生管线

1. **度量**：`tokenMeter.measure()` 按路由价 + 4 字符/token 启发式估算 surface；`contextPressure()` 只是给 UI 的投影，**不参与压缩决策**。
2. **触发**：`agent/pre-step` 压力检查、`agent/request` 换模型前按目标模型计价、`request-error` 收到 `CONTEXT_WINDOW_EXCEEDED` 强制缩、`/compact` 手动；默认 `thresholdRatio 0.8 / headroom 65536 / retainRatio 0.16`（本 profile 调为 0.72/0.12/32768/16384）。
3. **摘要**：只取 surface 上被遮蔽区间 + 系统消息 + tools，追加一条固定 `COMPACTION_INSTRUCTION`，要求 8 节 Markdown（Primary Request / Key Concepts / Files and Code / Errors and Fixes / Pending Jobs / Current Work / Next Step / Critical Context）；已有 `<compacted-summary>` 时要求"保留仍真事实、丢弃过时项、合并成单一摘要"——这是**递归二次摘要**，也是摘要漂移的结构性来源。
4. **事务**：`compaction/start`（锁）→ 摘要 → `compaction/summary`（含 summary/rawOutput/shadowedSeqs/tokenCount/usage）→ append 带 `surfaceOp:replace` 的 `user/message` → `compaction/end`；失败保面、未闭合锁 busy。
5. **裁剪**：`tool-result-pruner` 只处理 `tool/result`，>8192 字符换成"头 4096 + 标记 + 尾 1024"，纯语法、有损、原文仍在日志。
6. **日志**：append-only `session.v4.jsonl.zstd`；`seq` 只增不复用；`surface` 位置与 `seq` 序不同；`compaction/*` 全部 log-only。
7. **上下文组装**：`ctx.systemPrompt` 注册表 + `agent/pre-step`；渲染后的 system prompt 是 surface 节点；请求时 `deriveMessages()` 投影历史。
8. **扩展缝**：`CompactionEngine` 抽象类（每 context 一个实现）、`session/event`、`agent/*` 事件、`systemPrompt.section/context`、`tools.register`、`sessionQuery`、`storageDomain`、`sessionProjections`。

### 4.2 原生 vs Flow Tower 职责边界

| 维度 | 原生 DSH | Flow Tower（本 profile） |
| --- | --- | --- |
| 触发/阈值 | 全权（pre-step/request/request-error + `/compact`） | 继承；只改配置 |
| 区间选择 | 自尾部累积 retainTokens + tool-pair 吸附 | 继承 |
| 摘要模板 | 固定 8 节 + 递归合并 | 重写 `summarize()`：同模板 + 注入 ≤1800 字符项目记忆；**B 方案已重启验证生效**（§1.4.2） |
| 事务/锁/回退 | 全权 | 继承 |
| 裁剪 | pruner 8192/4096/1024 | 继承并启用 |
| 会话日志/回放 | 全权 | 继承；`dict_cite` 用 `sessionQuery` 回放 |
| 长期记忆 | **无** | 六维词典 + 关系 + 摘要树 + digest/map 注入 |
| 检索入口 | 无（模型只能重读文件） | 6 个工具 + 面板 + MCP |
| 证据 | 摘要不可验证；原文可 replay | 词条 `seq` 引文逐字回放；run-log 运行证据 |
| 回落 | `auto:false` 等 | 卸载 bundle 即回 `compaction-basic`（前提是挂载在会生效的层） |

### 4.3 原生边界（Flow Tower 不能假装解决的）

- 缩不掉 system prompt / tools / 会话前缀；单个超大 tool call 不可拆；pruner 只救文本型 tool result。
- token 估算是 4 字符/token 启发式，CJK 与 JSON Schema 被低估。
- 摘要只保留模型写出的文本；**模型没有原生检索入口**，只能重读文件。
- 递归合并摘要无一致性校验、无回滚；摘要漂移是结构性的。
- 每次 replace 从第一个被替换 token 起破坏 KV cache。
- 多 agent：`subagent_fork` 复制父前缀（含旧 checkpoint），父代理后续压缩不同步给子代理；v0.66 通过"共享项目 digest + 项目卷 updatedAt 版本代理"缓解（子代理已实机验证收到 `Shared project map`），但不做父子实时同步。

### 4.4 核心发现：host 平面挂载 ≠ 会话层生效

  ```yaml
  - id: compaction
    name: cordis:group
    group: true
    isolate:
      compaction: true
      toolResultPruner: true
    config:
      - id: compaction-basic
        name: '@deepseek-ai/dsh-compaction-basic'
      - id: command-compact
        name: '@deepseek-ai/dsh-command-compact'
      - id: tool-result-pruner
  ```
- 我们 bundle 的 patch 在 **host 平面** disable `compaction-basic` 并 insert `./compaction/index.js`。preset 的 isolate 组不受影响，会话内 `/compact` 走 preset 自己的 `compaction-basic`。
- 因此：`/api/status.compactionBackend=FlowTowerCompactionEngine` 只是 host 平面的事实；`compaction-runs.jsonl` 的 `backend` 字段也来自 host 平面，**会误导**。
- 影响：压缩摘要没有注入项目记忆；FlowTower 的"成为真实压缩后端"目标未达成。这也解释了此前 `summarizeHasFlowMemory=false` 与 engine 调试日志缺失。
- **已实施（B 方案）**：profile `cordis.patch.yml` 追加 `preset-cordis` 覆盖，`config.plugins` 全量复制并把 `compaction-basic` 的 `name` 改为 `file:///E:/dsh-plugins/flow-tower/compaction/index.js`；`skill-filesystem` 的 `baseUrl` 表达式替换为 asar 绝对路径；保留 `command-compact` 与 pruner。
- 仿真验证：用 Loader 的 `applyEntryPatches` 应用 web-app 预设 + 我们的 profile 补丁后，`preset-cordis` 行仍在，compaction 组为 `compaction-basic(file URL) / command-compact / tool-result-pruner`，23 个插件行完整。
- 重启后状态：新会话/subagent 能正常创建 → preset 组装通过（说明 `file://` 引擎模块已被成功导入）；`summarize()` 是否真正接管仍需一次 `/compact` 观察。
- `/compact` 验收：`C:\Users\wuhao\.dsh\flow-tower\compaction-engine-debug.log` 出现 `summarize start`；`compaction-runs.jsonl` 出现 `memoryChars>0` 行；`/api/status.lastSummarize.memoryChars` 可读（`lastSummarizeRun` 已合并 event + engine 两行）；失败则回滚 profile patch 并重启回原生 `compaction-basic`。
- 风险：DSH 升级后预设插件清单漂移，需要重新生成这份全量副本；文档与备份在 `design/22` 与 profile 目录的 `.bak-*`。

| bgx666/dsh-memory-tree | patch `BasicCompactionEngine.prototype.summarize`，节点树 + checkpoint 卡片 | 树形 checkpoint、UI、成熟压缩集成 | 单会话单树、patch 私有 API、无项目/任务/时间维度 | 我们走稳定 seam、项目本地、多维、可回执；它树视图更强 |
| qinghuaju/dsh-memory-tree | 旁路捕获 + 召回注入 + AST 可寻址 + hot/warm/cold | 跨会话长期记忆、分层存储 | 不管理压缩上下文、无逐字引文 | 我们压缩驱动 + 引文；它跨会话更强 |
| claude-mem | hook 捕获每次工具调用 + observer LLM + 三步检索 | 零操作捕获、15+ harness、渐进披露 | Bun/uv/Chroma/worker 重栈；摘要不可逐字回放 | 我们零服务、可重复、逐字回放；它捕获更细 |

| Flow Tower（本工具） | 压缩事件 → 确定性词典 + digest/map + seq 引文 | 零依赖、项目本地、证据硬、治理全 | 语义弱、压缩 provider 未生效（§4.4）、任务质量 | — |

> 同一 profile 不要同时启用两个"注入型"记忆插件：重复注入会争 token/注意力（README 已警告）。

### 5.4 super-agent / CarryOn / Cordis

- **super-agent**：领域模型把"上下文"当按角色/授权/预算投递的可见面，而不是真相存储；真相在 Ticket/Store。可借"投递不授权、按角色窄视图、截断给读指针"；不借"状态外置即上下文有界"（记录无界增长）。
- **CarryOn**：对象化上下文 + 验证后原子 fold，重点不是压缩率而是"可复用对象 + 校验"。我们已有 staging/validate/commit 的确定性版，缺 execution context 与语义校验；不引入 fold runtime（我们没有每步上下文装配权）。
- **Cordis**：effect/coeffect 的可逆组合解释了 DSH 插件"注册即可见、卸载即回滚"；我们的 `ctx.effect` 清理、legend/digest 注入应继续保持可逆语义。

### 5.5 多 agent / 子代理适配（v0.66）

DSH 的 `subagent`（spawn）与 `subagent_fork` 会产生独立 Session，但共享同一工作目录与同一项目 store。Flow Tower 的处理：

| 问题 | 设计 | 状态 |
| --- | --- | --- |
| 子代理没有自己的词典卷（首次压缩前） | `buildSharedDigest`：从**同项目最优卷**渲染 `Shared project map/brief`，头部标注 "N project sessions / this session has no dictionary yet" | ✅ 已实现 + 测试 + **重启后实机复验**（探针子代理首步收到 `inject: long-only`，status `scope=shared`） |
| fork 继承父前缀里的旧 checkpoint，父代理后续压缩不同步 | 子代理每步读共享项目 digest；项目卷 `updatedAt` 变化会作为版本代理使共享 digest 重新注入，覆盖旧快照 | ✅ 已实现（版本代理 + hash 去重） |
| 多个 agent 的任务互相不可见 | `store.openTasksForProject(project)` 聚合项目内所有卷的 open task，共享 digest 的 `Open` 行使用它 | ✅ 已实现 + 测试 |
| 并发写同一项目库 | 已有跨进程写锁 + WAL + `BEGIN IMMEDIATE`；StoreManager 按项目复用同一 store 实例；注入游标按 volume/`#project` 分开 | ✅ 已有，v0.66 增加共享游标 |
| 注入预算/策略 | 共享 digest 与自有卷走同一 `injection-policy`（checkpoint 新鲜度、任务类型、pressure、adaptive budget） | ✅ 已实现 |
| 父/子代理状态一致性 | 子代理的 checkpoint 是 fork 时快照；父代理新压缩只在共享 digest 版本变化时被看到 | 边界：**不做**实时父子消息同步，这是 DSH fork 语义 |
| 多 agent 共享任务的"归属" | 词条 citation 保留 `session_id`，可用 `dict_cite` 追溯是哪个 agent 产生的；未加 agent 角色字段 | 边界：不做角色标签（schema 不变） |

对比：super-agent 的订阅式扇出解决"投递"，CarryOn 的 execution context 解决"续跑"，我们的多 agent 适配只解决**共享项目记忆 + 任务可见性 + 并发安全**，不承担调度。

### 5.6 定位图

```
        确定性 / 可验证 / 可回溯
                    ▲
                    │   Flow Tower（项目本地、seq 引文、零依赖）
                    │   qinghuaju（旁路捕获、无逐字）
                    │   EverOS/basic-memory（md 真源）

                    │   graphiti / cognee / hindsight（图+服务）
```

Flow Tower 的稀缺位置：**左上角**——宿主内、确定性、可回溯、零服务；代价是语义智能与生态。研究方案在右下（语义强、工程弱）；平台在右下（生态强、依赖重）；bgx666 在中上（树 UI 强、可回溯弱）。

## 6. 综合定位

### 6.1 真实差异化（仍然成立的 5 条）

1. **项目本地、随代码库走**：`<项目>/.flow-tower/`，自动 gitignore，多会话共享，可迁移。
2. **原文无损可回溯**：词条只存 `seq` 句柄 + 短摘录，`dict_cite` 从 session log 逐字回放；跨会话可用。
3. **压缩驱动、零人工、零外部服务**：确定性抽取，失败回退；不需要向量库/图数据库/LLM key。
4. **多维检索面**：项目/模块/功能/任务(open-done)/时间/章节/人物 + 类型化关系 + 摘要树；工具平均 2 次调用直达。
5. **工程治理与规模证据**：模块契约/依赖图/LOC 门禁/73 单测/8.4M 字符与 10 万边基准；运行证据（run-log/metrics）可审计。

### 6.2 客观弱项（v0.65 版，按影响排序）

1. **压缩 provider 未在会话层生效**（§4.4）——目标级缺口。
2. **语义召回弱**：无 embedding / rerank；同义、跨语言、主题召回不如 Graphiti/mem0。
3. **无递归摘要树**：只有确定性分类+抽取式摘要；RAPTOR/MemTree 的递归聚类没有。
4. **任务/决策质量**：启发式抽取 + token 重叠闭环，长句/碎片仍多。
5. **不压缩就不编纂**：短会话/无压缩会话无覆盖；缺 event-spine 兜底。
6. **时效缺失**：decision/task 无 `valid_from/valid_to/superseded_by`；旧决策可能和新决策同时出现在注入里。
7. **单写者**：多实例并发不保证合并，只保证不写坏。
8. **UI/生态/分发**：只读面板、无浏览器 E2E、tarball 版本落后（dist 里最新 0.35.1）。

### 6.3 什么场景不该用 Flow Tower

- 短会话、一次性脚本：没有压缩就没有记忆，digest 反而增加常数开销。
- 语义问答/跨语言知识库：词法检索不是它的强项，应上 embedding。
- 多 agent/多人协作共享记忆：单写者 + 单项目库，不适合并发写；super-agent 式调度不该由它承担。
- 非 DSH 环境：深度绑定 DSH 的 event/service/session 形状，没有 adapter。

### 6.4 分档

| 档位 | 方案 | 判据 |
| --- | --- | --- |
| T1 平台/生态 | mem0、Graphiti、Letta | 语义/平台成熟，但非 DSH 原生、依赖重 |
| T1 DSH 深度集成 | **Flow Tower**、bgx666、qinghuaju、claude-mem | 原生、可落地；各有强弱 |

| T2 专用/辅助 | ReadAgent、HORMA、aider、Serena、PageIndex、LLMLingua | 单点强，不能当记忆系统 |

## 8. 结论

- **论文侧**：Flow Tower 的形态（BM25/词法 + seq 引文 + 分层工具 + 预算注入）不是"过渡方案"，而是被 APDMem/ReadAgent/HTM 正面支撑的**低成本可回溯基线**；研究方案真正领先的是语义聚类与递归摘要，代价是写放大与不可回溯。
- **原生侧**：DSH 已经把压缩做成一个可靠事务，Flow Tower 的价值在事务之后——把"不可检索的摘要"变成"可检索、可引用的项目记忆"；一旦试图重造触发/事务/裁剪，就是负收益。
- **开源侧**：我们在"项目本地 + 零服务 + 逐字回放 + 压缩驱动"上是稀缺组合，短期不需要向平台化看齐；要补的是语义、时效、捕获兜底，而不是生态。
- **最关键的下一步不是新功能，而是让 FlowTower provider 在 preset 层真正生效**；该验证已于 2026-11-15 12:31 通过（engine 接管、run-log `memoryChars=1799`、status 可读），"真实 DSH 压缩路径"落地，v1.0 结案；后续只做 backlog。
