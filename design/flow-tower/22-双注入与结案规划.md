## 0. 结论先行

1. **DSH 原生是"短程精确"**：一个 8 节 checkpoint（Primary Request / Key Concepts / Files / Errors / Pending / Current Work / Next Step / Critical Context）替换掉旧历史，保留最近工作细节；配 pruner 与 KV cache。缺点是摘要不可检索、多轮后漂移、模型只能重读文件。
2. **Flow Tower 是"长程可回溯"**：3000+ 词条、2 万关系边、`seq` 引文、模块地图、时间线；缺点是不压缩就不编纂、语义弱、常驻注入有成本。
3. **没有一律"双注入最好"**：两者同时注入时，最近的 Progress/Change log 会与 checkpoint 重复，既花 token 又可能给出两个版本的"最近状态"。默认实现改为 **任务类型 + checkpoint 新鲜度 + 压力** 驱动的 `auto`：
   - 新会话/无 checkpoint → **long-only**（单注入：只有长程）；
   - 新鲜 checkpoint + coding/research/history → **dual-lite**（双注入但去重：长程只给定向）；
   - 新鲜 checkpoint + planning → **dual**（双注入：计划需要近期约束 + 长程决策/未完成项）；
   - checkpoint 超过 2 轮 → **dual**（摘要已旧，长程补最近变化）；
   - 新鲜 checkpoint + 普通对话 / 压力 ≥0.85 → **short-only**（单注入：只用原生 checkpoint）。
4. **结案的最后一项目标级欠账"压缩 provider 未在 preset 层生效"已关闭**（`21` §4.4/§1.4.2）：B 方案（preset 覆盖）重启后验证通过——engine 调试日志 `summarize start`、run-log `memoryChars=1799`、status `lastSummarize.memoryChars=1799`。v1.0 已结案（§7）。
5. **多 agent 是已落地的一等能力**：无自有卷的会话/子代理读取共享项目 digest，跨卷聚合 open task；并发写仍由项目写锁保证，不做父子实时同步。

## 1. 两套机制的分工

| 维度 | DSH 原生（短程） | Flow Tower（长程） |
| --- | --- | --- |
| 事实源 | 会话日志 + 最新 checkpoint 文本 | 项目词典 + `seq` 引文（原文仍在日志） |
| 覆盖范围 | 最近一次压缩以来的工作细节（精确路径/命令/错误/下一步） | 跨压缩、跨会话的项目全貌、任务/决策/模块/时间线 |
| 写入成本 | 每次压缩 1 次 LLM（本会话 25.4s / 13,170 字符摘要） | 压缩事件后确定性编译（毫秒级，零 LLM） |
| 常驻成本 | checkpoint 约为数 k token，随历史保留 | digest/map 约 700–800 token/次，版本变化才注入 |
| 检索 | 无（模型只能重读文件/再压缩） | 6 个 `dict_*` 工具 + 面板 + MCP，2 次调用直达原文 |
| 失效模式 | 摘要漂移、细节丢失、递归二次摘要、不可验证 | 词法召回弱、任务质量、注入上限 40 次/卷、依赖事件 |
| 适合 | 一次任务内的"接着做" | 跨天的项目连续性、"为什么/之前/进度"回查 |

一句话：**短程负责"现在做到哪"，长程负责"这个项目是什么、为什么走到这"。**

## 2. 任务类型 × 注入矩阵（v0.66 默认 `injectionMode: auto`）

| 任务类型（判定信号） | checkpoint | 压力 | 注入模式 | 长程内容 | 理由 |
| --- | --- | --- | --- | --- | --- |
| coding（edit/write 工具或修改/实现/修复等） | 新鲜（≤2 轮） | <0.85 | **dual-lite** | Goal/Open/Modules/Traverse，去 Latest/Progress/Change log，预算 ×0.6 | 最近细节由 checkpoint 负责；长程只给定向 |
| research / history（读工具、论文/之前/进度） | 新鲜 | <0.85 | **dual-lite** | 同上 | 问题需要的是长程指针，不是重复最近流水 |
| planning（规划/方案/设计/todo） | 任意 | <0.85 | **dual** | 完整 map/brief | 计划需要决策、未完成项与近期约束并存 |
| coding / research | 已旧（>2 轮） | 任意 | **dual** | 完整 map/brief | checkpoint 不再描述当前工作，需要长程补最近变化 |
| general（无明确信号） | 新鲜 | <0.85 | **short-only** | 不注入 | 原生 checkpoint 已够，省 token |
| 任意 | 新鲜 | ≥0.85 | **short-only** | 不注入 | 先保窗口，让宿主压缩处理 |
| 任意 | 不存在（新会话/未压缩） | 任意 | **long-only** | 完整 map/brief | 长程是唯一连续性来源 |

**标记**：注入头会带一行机器可读标记，例如
`[flow-tower] Project map · 超级上下文 · 6 open / 21 done · inject: dual-lite · short: checkpoint 0t ago · task: coding`
模型据此知道：checkpoint 是权威近期状态，map 只是长程定向，不要复述。

**配置**：
- `injectionMode: auto`（默认）/ `dual`（永远完整双注入，保留旧行为）/ `off`（不注入）；
- `adaptiveDigestBudget` 仍先生效，`dual-lite` 再乘 0.6、下限 400 token；
- 任务判定失败或 `deriveMessages()` 不可用时**回退到旧的完整 digest**（保守降级，不阻断）。

**可观测**：
- `digest-injection` metric 增加 `mode / taskKind / checkpointAgeTurns / budgetScale / reason / skipped / scope / sessions`；
- `/api/status` 增加 `injectionMode` 与 `lastInjection`（最近一次注入或跳过的计划）。

### 2.1 多 agent 适配（v0.66）

DSH 的 `subagent`（spawn）与 `subagent_fork` 各自拥有 Session，但共享同一 cwd 与同一项目 store。Flow Tower 的适配原则是"共享长程、隔离短程"：

| 场景 | 行为 |
| --- | --- |
| 子代理/新会话还没有自己的词典卷 | `buildSharedDigest` 从**同项目最优卷**渲染 `Shared project map/brief`，头部标 `N project sessions` + "this session has no dictionary yet"；模型知道这是项目记忆而非自己的历史 |
| fork 继承的旧 checkpoint | 共享 digest 的版本代理 = 项目卷最大 `updatedAt`；父代理后续压缩会触发共享 digest 重新注入，覆盖 fork 快照的陈旧信息（hash 去重，不会重复刷） |
| 多 agent 的任务互相不可见 | `store.openTasksForProject(project)` 聚合所有卷的 open task，共享 digest 的 `Open` 行使用它；`dict_browse({project})` 仍可看全项目 |
| 并发写 | StoreManager 按项目复用同一 store；跨进程写锁 + WAL + `BEGIN IMMEDIATE`；注入游标按 `volumeId` 或 `${volumeId}#project` 隔离 |
| 注入策略 | 共享 digest 与自有卷走同一 `injection-policy`（checkpoint/任务/压力/adaptive budget） |
| 不做 | 父子实时消息同步（DSH fork 语义边界）；agent 角色字段（不扩 schema）；跨 agent 调度（super-agent 的领域） |

验收：`buildSharedDigest` 单元测试、apply 集成测试（子代理无卷注入）、跨卷 open task 聚合测试；共 80/80。

### 2.2 语义召回与前端搜索（v0.66.2）

**现状**：词典检索的可靠信号仍是词法（TF-IDF + 双语同义词 + 关系近邻），稀疏 TF-IDF/共现的"semantic-lite"不是神经语义。新增 `eval/search-recall.mjs`（12 词条 / 50 查询 / top-5）：

| 查询类型 | lexical | sparse semantic | hybrid |
| --- | ---: | ---: | ---: |
| exact headword | 1.000 | 1.000 | 1.000 |
| truncated | 0.917 | 0.917 | 0.917 |
| gloss fragment | 0.917 | 0.667 | 0.917 |
| cross-language | 0.929 | 0.143 | 0.929 |
| **overall** | **0.940** | **0.660** | **0.940** |

**决策**：
- 默认从"lexical 或 semantic 二选一"改为 **hybrid = 词法顺序优先 + 稀疏语义补位**；纯 RRF 融合实测把正确词法命中挤出 top-5（0.88 vs 0.94），因此不采用。
- 真正的语义升级路径是 **DeepSeek smart search（查询改写 + 候选重排）** 和 **可选 embedding**，不是把 semantic-lite 说成"语义召回"。
- 修复 `/api/smart-search` 缺少 `searchText`/`smartSearch` import 的 500 bug，并加 10 分钟内存缓存（同一面板重复查询不再重复两次 LLM 调用）。

**前端搜索修复**（`lib/web-page.js` / `web-page-style.js` / `web-page-script.js`）：
- 防抖 320ms + Enter/Escape；类型/排序/模块前缀过滤；结果卡片（kind/status/module/score/gloss + matched/sources/reasons 徽章）；
- ↑/↓ 键盘导航、Enter 打开词条与引文；加载更多；零结果时提示换过滤或"智能重排"；
- 所有内容用 `textContent` 渲染，避免词典内容注入 HTML。

**后续**：smart 低分自动回退 + 缓存、alias 挖掘、ASCII 前缀/轻量 stemming、真实会话查询集扩充 eval（见 `docs/search.md`）。

## 3. 为什么这样判（依据）

- **短程 > 长程的重复是负收益**：DSH checkpoint 已包含 Current Work / Next Step / Files；Flow Tower 的 Latest/Progress 若同时注入，等于把"最近的流水"说两遍，还可能在两次注入之间给出不一致的状态。论文侧同构证据：GraphRAG C0 层间无显著差异、ReadAgent 复现"分层摘要不如全量原文"，说明"多一层未必更好"。
- **长程不能省**：APDMem 证明 73.7% 查询止于浅层、但 `read_raw` 掉 5.9% 是最大单项；HTM 证明没有单一基质通吃。所以不是"只留短程"，而是"在短程新鲜时把长程压到定向层"。
- **任务类型决定最近细节的需求**：coding 的下一步强依赖 checkpoint 里的文件/错误；planning 强依赖长程的决策与未完成项；general 对话两者都不强。
- **压力阈值已经有实证基础**：adaptive budget 的 0.55/0.7/0.85 三档与宿主的 tokenMeter 同源；0.85 时再注入长程只会加速下一次压缩。

### 4.4 明确不做（结案边界）

- 不内置 embedding / rerank / 向量库；
- 不把 skills 文本嵌入插件（skills 按需加载，插件提供能力）；
- 不做每轮 LLM 总结 agent、agent 改 digest、agent 删记忆；
- 不做多主并发、跨机同步、平台化 UI；
- 不在 v1.0 结案前引入新的知识类型/新工具（只修 bug 与证据）。

## 6. 风险与回退

| 风险 | 触发 | 回退 |
| --- | --- | --- |
| preset 覆盖写坏会话压缩 | 重启后 `/compact` 报 `busy/summary` 或 engine 加载失败 | 恢复 profile `cordis.patch.yml` 备份（`.bak-<ts>`），重启回 `compaction-basic` |
| DSH 升级导致 preset 插件清单漂移 | 升级后新插件缺失/报错 | 重新从新版 `dsh-web-app/presets/cordis.patch.yml` 生成覆盖（脚本步骤见 21 §4.4） |
| 多个 flow-tower 实例同时写共享库 | 多窗口/多实例 | 已有项目写锁；仍建议一个项目一个实例 |
| 任务分类误判导致该注入时跳过 | `lastInjection.mode=short-only` 但任务其实需要长程 | 设 `injectionMode: dual` 强制回旧行为 |
| dual-lite 去重过度（丢关键进度） | 模型反馈"不知道最近改了什么" | 设 `injectionMode: dual` 或把 checkpoint 阈值 2 轮调到 4 轮 |
| 注入标记增加 token | 每步多 ~10 token | 可接受；只在版本变化时注入 |
| 真实会话未覆盖某任务类型 | 观测样本少 | 以 metrics 采样继续观察，不阻塞结案 |

## 7. 一句话回答"双注入还是单注入"

**默认"长+短"双注入，但按任务去重；短任务/无长程需求时单注入。**
- 需要"接着做"→ 短程为主，长程只给定向（dual-lite）；
- 需要"回看/计划/跨天"→ 长+短全量（dual）；
- 新会话 → 只有长程（long-only）；
- 闲聊/高压 → 只有短程（short-only）。
