## 2 机制层拆解

### 2.1 ReadAgent = 有序 gist 列表 + 页句柄原位展开（注意：它**没有树**）

**数据结构**（[原文] R:222-226、273-275、330-334 综合）
```
page_i   = (page_no, char_span, raw_text)          # 原文，唯一真源
gist_i   = (page_no, gist_text)                     # "shortening"，非摘要
memory   = [⟨Page 1⟩gist_1, ⟨Page 2⟩gist_2, …]      # 有序、定长位置
lookup   = 用 raw_text_i 原位替换 memory 中的 gist_i
```
**三步伪代码**（[原文] R:104-119 与 3.1/3.2 节）
```
1 paginate: 截一段 ≤max_words 的续文 → 在段落间插编号标签 ⟨k⟩（只在 min_words 之后插）
   prompt: "choose a label where it is natural to break reading…explain"   # R:244-263
2 gist:     对每个 page 调 "Please shorten the following passage. Just give me a shortened
            version. DO NOT explain your reason." → 前置 ⟨Page N⟩ 后拼接          # R:264-280
3 lookup:   P 模式=一次请求多个页（上限 1–5/1–6，附 "DO NOT select more pages…"）；S 模式=每轮
            一页 + "STOP"；选中页原位替换 gist 后再回答                          # R:291-368
```
**真实超参数**（[原文] R:1642-1657；R:1314-1317）QuALITY/QMSum `max/min=600/280`；NarrativeQA Gutenberg `3000/500`；movie scripts `1000/600`；默认 280/600。压缩率定义 CR=100·(1−in-context/full-context)（R:431-439）。

**关键结果**（[原文]）QuALITY：全量原文 85.83% < ReadAgent-P 1–6 页 86.91% < S 1–6 页 87.17%；只用 gist 77.52%（R:616-643）。"逐查询决定读几页"的模型自主性真实存在。NarrativeQA Gutenberg test：ReadAgent-P 1 页 LR-1 59.98，BM25 top-4 53.60（R:713-724 vs 800-805）；有效上下文放大约 20×（R:8-9）。单词消耗对 QuALITY dev：1 页查找省 25.4%、2 页省 20.4%（R:393-404）。

**失败模式**（[原文]+【推断】）
1. **gist 本身受上下文窗口约束**：`the database cannot scale arbitrarily, since the size of the gist memory is limited by the LLM's context length`（R:183-187）；NarrativeQA 靠"合并页 + 重 gist"硬压（R:2181-2185）。→ 平铺 gist 不是可扩展结构，必须分层或分树。【推断】
2. **总结型任务模型会拒绝下钻**：QMSum 上 `I don't need to look up any pages. I can summarize the whole meeting based on what I already remember.`（R:1211-1216）→ 句柄机制在"要全局概括"时不被使用，正对应分总层要解决的场景。
3. 长文档下 gist 层的召回只能靠页号，**页之间无层级、无父子、无跨页链接**。
4. 幻觉风险被作者单列为 impact：detail 被 gist 剔除后模型可能自行补细节（R:1337-1350）。
5. 分页方式影响效果：LLM 语义分页 86.83% > 等长分页 85.71%（R:1273-1279）；页越大压缩率越高但"gist-only"准确率下降（R:1294-1313）。
6. GPT-3.5 上 P 模式几乎只用 1.0 页（提示预算未被用满，R:1614-1616）。

### 2.2 GraphRAG = 实体图 → 层级社区 → 自底向上社区报告 → map-reduce 全局问答

**索引期数据结构**（[原文] G:209-298、1515-1575）
```
chunk        = 600 token, overlap 100                                    # G:407-412
entity       = (name, type, description)                                 # G:229-234
relationship = (source, target, description, strength 1–10)              # G:1456-1468
claim        = 关于实体的可验证事实陈述                                     # G:240-247
community_i  = Leiden 层级划分，互斥且完备(MECE)，逐层递归下分                 # G:265-276
report(c)    = {title, summary, rating 0–10, rating_explanation, findings[5–10]{summary,explanation}}
               + grounding: [Data: Entities(5), Relationships(37,38,+more)] # G:1523-1576
```
**社区摘要构建**（[原文] G:286-298）：叶社区按"边两端节点度数之和"降序装入 element summaries，直到 token 上限；高层社区若装不下，则按 element-summary token 数降序**用子社区摘要替换其元素摘要**，直到装得下（自底向上递归）。
**查询期 map-reduce**（[原文] G:306-315）：社区摘要**随机打乱**再切块（防止相关信息集中在同一窗口）→ 并行 map 出部分答案并打 0–100 helpfulness 分 → 过滤 0 分 → 按分数降序装入 reduce 窗口直到 token 上限 → 生成全局答案（G:1677-1680 "analysts' reports ranked in descending order of helpfulness"）。
**真实超参数** [原文]：context window 固定 8k（试 8k/16k/32k/64k，8k 综合最好，G:1364-1369）；实体抽取带 self-reflection（logit bias=100 强制 yes/no，续写 "MANY entities were missed…"，600 vs 2400 token chunk 实体数近 2×，G:1317-1328）；实体匹配用 exact string match（G:260-264）；索引耗时 Podcast ~1M token 语料 **281 分钟**（16GB VM + gpt-4-turbo，G:436-442）。图规模：Podcast 8,564 节点/20,691 边；News 15,754/19,520（G:476-477）。
**层级成本/效果**（[原文] G:850-896、899-911、954-955）：Podcast C0–C3 单元数 34/367/969/1310，token 26,657/225,756/565,720/746,100（TS=1,014,611）；C0 比 TS 省 9–43× token；C0 vs SS 全面性胜率 72%、多样性 62%，且 **C0–C3 之间无统计显著差异**；C0 vs TS 在全面性上无显著差异（p=1 / 0.17，G:1857-1866）。
**失败模式**：① 只解决"全局概括"，不解决定位（本论文未实现 local search，G:1050-1059 把 hybrid 留作 future work）；② 社区报告丢细节（empowerment 结果参差，作者归因于"缺少例句/引文"，G:897-898）；③ 索引成本高、且图索引是**一次性构建**（无增量机制）；④ HiRAG 对它的批评：global search 成本过高且不用局部实体描述（H:517-522）；⑤ 仅 2 个 ~1M token 语料、LLM-as-judge 无 gold（G:972-979）。

### 2.3 HiRAG = KG 逐层聚类 + summary entities 作 semantic hub + 三层检索（local/bridge/global）

**数据结构与构建**（[原文] H:327-384）
```
L0 = V0                       # 基础 KG：chunk→LLM 抽实体 V0 与关系 E0
L_i = ∪_{S∈C_{i-1}} LLM(S, X) # 对上一层实体 embedding 做 GMM 聚类 C_{i-1}，
                              # 每个簇用"元摘要实体表 X"引导 LLM 生成 summary entities
E_{i-1,i} = {簇内实体 → 其 summary entity}   # 跨层边；层内 summary entities 之间无关系
```
X 是"organization/person/location/event/technology…"这类**通用概念小词表**，用于引导上层抽象（H:360-370）。社区用 Leiden 在**分层 KG** 上计算，**实体可属于多个社区**（与 GraphRAG 的互斥划分不同，H:385-389）。
**动态层数**（[原文] H:1029-1077）
```
CS_i = 1 − Σ_{S∈C_i} |S|(|S|−1) / (|L_i|(|L_i|−1))       # 簇越碎 → CS 越接近 1
if  CS_i 相对 CS_{i-1} 的变化率 < ε = 5%  then 停止再建一层
```
Figure 4 显示层数（x 轴 0–8）增加时 CS 上升后趋稳；论文**没有**逐数据集报告 k 值〔边界〕。
**检索三层**（[原文] H:415-477；伪代码 H:1675-1701）：local = 与 query 相似度 top-n=20 实体描述；global = 与这些实体相交的社区报告；bridge = 每个社区取 top-m 关键实体，按序求**最短路径**并收集路径上的三元组。生成时三层一起进 context。
**关键结果**（[原文]）vs GraphRAG 总体胜率（GPT-4o 评判，Mix/CS/Legal/Agriculture）：64.1/35.9、64.0/36.0、54.5/45.5、54.0/46.0（H:699-707）；消融 w/o Bridge（去掉桥）总体掉到 47.3/42.5/44.0/42.0（H:919-927）；w/o HiIndex（换平 KG）掉到 42.4/40.0/46.5/48.0（H:875-882）→ **层级与桥都有正贡献**。bridge 上下文对 global/local 信息的 token 级召回：global 38.6–53.4%、local 64.5–83.1%（H:993-1007）。
**成本**（[原文] H:1085-1225 + 语料 H:1482-1497）：索引 token / 语料 token —— Mix 21.9M/0.63M≈**35×**、CS 56.0M/2.21M≈25×、Legal 106.4M/5.28M≈20×、Agriculture 96.1M/2.03M≈**47×**；索引耗时 Mix 17,208 s / CS 44,994 s / Legal 115,232 s / Agriculture 50,920 s（≈4.8–32 小时）；论文自承"indexing is offline"，Mix 索引约 **7.55 USD**。检索侧 **0.00 token、1.00 次 API 调用、0.85–2.04 s/query**（H:1218-1225）。
**失败模式**：① 索引 token 放大 20–47×，会话级不可能实时负担；② 关系排序仍只靠 LLM 打分（作者列为 limitation，H:1247-1254）；③ summary entity 质量无独立评测，只有端到端胜率〔边界〕；④ 层内 summary entities 之间无关系，上层结构必须借跨层边遍历（H:382-384）→ 上层不能当"兄弟可比较"的目录用。

### 2.4 三者横向对比（构建性质是本项目最关心的列）

| 维度 | ReadAgent | GraphRAG | HiRAG |
| --- | --- | --- | --- |
| 结构 | **无树**：有序 gist 列表 + 页句柄 | 实体图 → 层级社区 → 报告树 | KG 逐层抽象 + 社区（可重叠） |
| 叶层装的是 | **原文页**（可原位展开） | 实体/关系/claim 的短描述（无原文段） | 实体/关系描述（无原文段） |
| 构建性质 | **读入时一次性**、任务无关、可摊薄（R:393-398） | **离线索引**（281 min/1M token） | **离线索引**（论文原话 indexing is offline，H:1220） |
| 查询期成本 | 每次 1–N 次页展开调用 | map 覆盖该层全部社区（C0=34/55 单元） | 0 LLM token（embedding + 图算法）+1 次生成 |
| 是否支持增量 | 无（靠"合并页重 gist"硬改） | 无（重建索引） | 无（重建分层 KG） |
| 最可迁移零件 | 页句柄 + 原位展开 + 语义分页 | 社区报告 schema + map-reduce + helpfulness 闸 | CS_i 动态层数 + 元摘要词表 + bridge |

**三篇互相矛盾、但恰好能确定"分层值不值得"**：ReadAgent 的附录 H 用最好努力复现 MemWalker 树搜索只得 66.73%（全量原文 85.83%，ReadAgent 86.88%），11.7% 搜索失败，并给出结构性原因：`the hierarchical summary structure makes it difficult to reason over related but distant information at the same granularity`（R:2158-2176）；GraphRAG 则给出 C0–C3 层间无显著差异（G:954-955）；HiRAG 给出分层 KG 有正贡献（H:930-954）——**结论不是"分层好/坏"，而是"分层只在需要跨实体抽象时有用，在需要远距离同粒度证据时有害"**。这条对流动树是硬约束（见 4.5）。

### 3.2 更正（00 有错，必须改）

- **C1〔§2 表第一行〕"递归摘要 + 叶层留原文 | RAPTOR、MemTree、GraphRAG、HiRAG"——对 GraphRAG/HiRAG 不成立。** 两篇的叶层是**实体/关系/claim 的描述**，原文段落并不在索引结构里：GraphRAG 的社区摘要由 `element summaries (for nodes, edges, and related claims)` 组装（G:286-298），grounding 只到 `Entities(5) / Relationships(37)` 这类记录 id（G:1564-1575）；HiRAG 的基础结构是 `G0={(h,r,t)}`（H:296-298），检索只取实体描述 + 社区报告 + 路径三元组（H:470-477）。两篇均未描述"原文段落作为叶节点"。→ 建议 00 把该行拆成「递归摘要 + **实体/三元组叶**（GraphRAG/HiRAG）」与「递归摘要 + **原文叶**（RAPTOR/ReadAgent 页）」两条能力。这条直接决定：**原文回溯句柄不能指望 KG 系论文，只能抄 ReadAgent 的页模型。**
- **C2〔§3.3〕把 ReadAgent 归入"离线一次性构建"不准确。** ReadAgent 没有外部索引，是**读入时（per-document）构建、查询期零构建**；原文 `generating gists is an one-time effort … can be amortized when the same context is reused for multiple tasks`（R:393-398），且明确 `the database cannot scale arbitrarily, since the size of the gist memory is limited by the LLM's context length`（R:183-187）。→ 00 的"离线/在线"二分应改为三分：**离线索引（GraphRAG/HiRAG）/ 读入时构建（ReadAgent、bgx666 压缩）/ 逐查询计算**。
- **C3〔§3.2〕HiRAG 的 `ϵ=5%` 判据写窄了。** 不是 `CS_i<5%`，而是 **CS_i 相对上一层的"变化率" < 5%**（H:1074-1077：`stop constructing another layer when the change rate of cluster sparsity is lower than ϵ`）；且 k 是每篇数据动态得出，论文未给具体 k〔边界〕。
- **C4〔§2 表第三行〕"按查询决定看多深"漏了最直接的 ReadAgent。** 它让 LLM 自己决定"读 1–5 页 / 每轮 1 页 / 停止"，QMSum 上模型还会主动拒绝下钻（R:291-368、R:1211-1216）。→ 该行应加入 ReadAgent（同时保留在"原文回溯句柄"行，它是唯一两项兼备的系统）。

### 3.3 补强（00 没写、但对分总层/流动树有决定性的）

- **B1 ReadAgent 是"扁平 gist vs 树搜索"的独立反证**：MemWalker 树搜索 66.73% + 11.7% 搜索失败 vs ReadAgent 86.88%（R:2158-2176）。00 §2 只引了 RAPTOR 的 collapsed-tree 结论；此条来自另一篇、另一个团队，**两条独立证据同向** → 流动树必须保留"全层压平检索"旁路，不能只靠逐层下钻。
- **B2 分总层不需要深层级**：GraphRAG C0–C3 无显著差异（G:954-955），root 级只要 2.6%/2.3% 的 token（G:850-896）。→ 直接支持 01 §8.2 的"路由视图极窄"：**每棵树只需要 root 级一句话画像，不必给分总层建多层摘要**。同时 C0 vs TS 无显著差异（G:1857-1866）说明"图索引的全局总述"并不比纯文本 map-reduce 更准，只是更省 token——省 token 才是它的贡献。
- **B3 "跨树层空白"要收窄**：单语料的全局总述有完整实现（GraphRAG global search：全量社区摘要 map-reduce）。真正空白的是**"多树/多会话 + 按查询先路由再进树"**——GraphRAG 是全量扫描，不是路由（G:306-315）；HiRAG 的 global 是"与命中实体相交的社区"，也不是跨语料路由（H:431-442）。→ 00 §6.1 的结论仍成立，但"分总层"可以拆成"总述（有原型，抄 GraphRAG）"与"路由（无原型，自研）"两半。
- **B4 跨树桥有结构原型**：HiRAG 的跨层边 `E{i-1,i}` + 跨层最短路径 bridge（H:355-359、H:443-477、H:1693-1699）就是"把语义相近但结构遥远的点连起来"的机制，可当跨树链接模板；但它在同一 KG 内、离线算，**不能直接当在线跨树迁移**。【推断】
- **B5 ReadAgent 自己点名了助手场景**：`For a very long event history, such as a conversation, we may consider further compression of the older memory with iterative gisting … useful for applications such as assistant agents, where context lengths can grow arbitrarily long over time`（R:2153-2157）。可作为插件立项的文献动机引用。
- **B6 前缀缓存没有文献依据**：三篇 0 处讨论 prompt/prefix cache（见 §1 grep）。00 §6.3 的"流动 ↔ 缓存冲突"依旧是**工程推断**，应保持在讨论层，不能写成事实。

### 4.2 分总层（抄 GraphRAG；目标模块：新增 `router.js` + `overview.js`）

- **路由视图 = C0 画像**：每树一条 `{tower_id, title, summary≤2 句, importance 0–10, refs[], last_active, token_cost}`，常驻 prompt 的**稳定段**（工具描述或系统提示尾部的固定块），只在树生命周期事件（新建/根合并/归档/迁移）时改写。依据：C0 只占 2.6% token 且层间无显著差异（G:850-896、G:954-955）。
- **总述视图 = map-reduce**：map 阶段对选中的树各生成一段"部分答案 + 0–100 helpfulness"；过滤 0 分；reduce 按分降序装入 token 上限后合成。**helpfulness 分就是 01 §8.2 要的"预算控制器"**（G:306-315、G:1741-1745）。
- **报告 schema 直接复用**：`{title, summary, rating(0–10), rating_explanation, findings[5–10]}`，可见字段降为 `summary + findings + refs`（G:1523-1562）。
- **引用格式**：`[Data: Node(12), Msg(88), +more]`，单条最多 5 个 id 后接 `+more`（G:1568-1574）。→ 总述视图里的每句话都能落到节点/消息序号，**这是"总述写坏导致全塔失联"的解药**（01 §8.2 硬规矩）。
- **总述视图不进常驻**：只在 tool result 中按需返回，带 `version/timestamp`，与 01 §8.2 一致。
- **成本锚点**：C0 一次查询 34 单元 / 26.7k token（Podcast，1M token 语料，G:866-885）。DSH 若 20 棵树 × ≤150 token 画像 ≈ 3k token 常驻，量级可行【推断】。

### 4.3 流动（抄 HiRAG；目标模块：新增 `flow.js`，由压缩事务/静默期调用）

- **动态层数判据**：每层节点 embedding 做聚类（现有 merge 已产生父/子分区，可直接当 C_i），算 `CS_i`；当 `CS_i` 变化率 <5% 时停止新增层，或触发"压平/合并同层"。注意 DSH 是 **merge 驱动**、不是 GMM 重建，需在每次静默期批量重算而不是每轮算。【推断】依据 H:1029-1077。
- **元摘要词表 X**：给父层摘要 prompt 一张固定概念表（建议：`任务/决策/约束/文件/人物/结论/阻塞`），让不同树的父节点**可横向比较**——这是 HiRAG 里最便宜、最可抄的零件（H:360-370）。分总层要路由，跨树父节点必须同构；否则"A 树的 L2"和"B 树的 L2"没法拼。
- **跨树桥（第二版）**：抄"每个社区取 top-m 关键实体 + 关键实体间最短路径"（H:443-477）。DSH 第一版可降级为：分总层只记 `shared_hubs[]`（两棵以上树共享的 hub 节点 ID），路由时作为"两树相关"的证据返回。
- **构建/查询分离**：HiRAG 索引 20–47× 语料 token、检索 0 token（H:1085-1225）→ DSH 只在**批量窗口/静默期**做 LLM 建层（这部分按 HiRAG 是重活），**每轮只允许 embedding + 图查**。按 35× 放大估算，一个 20 万 token 的会话做全量实体级索引要 ~700 万 token LLM 调用，不可接受；所以第一版应**跳过实体抽取**，只对已压缩节点做 embedding + 聚类【推断】。

### 4.4 前缀缓存影响（**全部【推断】**，三篇无实验）

1. **原位展开的缓存代价**：ReadAgent 式原位替换保持页位置稳定，但展开后其后所有 token 位移 → 该页之后的前缀缓存全部失效；若展开的是最后一个页，则前缀全复用。→ 建议双模式：常驻块只放 gist（稳定），展开内容以 tool result **追加在末尾**；只有在需要叙事连续性时才原位替换。二者必须由配置项控制，并在 status 里记录展开次数。
2. **渲染顺序稳定化**：树内节点若按"活跃度/最近访问"排序渲染，每次访问都会重排 prompt → 必然失效。建议 prompt 中的树/节点顺序固定按 `node_id`（创建序），活跃度只用于路由视图与 UI。这与 01 §8.1 的"结构变更静默期"同理。
3. **路由视图写入频率**：每次写画像 = 常驻段一次失效。只在生命周期事件写；总述视图写进 tool result 不碰常驻段。
4. **embedding 路由完全不进 prompt**：HiRAG 的 0-token 检索（H:1085-1225）说明"用向量挑树"可以发生在 prompt 之外——最省缓存的做法是 `route_intent` 工具内部做向量匹配、只回 1–2 棵树 ID；常驻画像只负责让模型"知道有这个工具"。
5. **建议在插件内埋点**：`cache_hit_tokens / cache_miss_tokens / tree_rewrites`，用真实数据验证"流动 vs 缓存"的代价——这条目前文献空白（00 §6.3 仍是推断）。

### 4.5 建议的插件设计约束（给 lead 的收敛版）

1. **两库分离**：查询路径只允许 embedding + 窄 prompt（HiRAG 先例）；LLM 建树/建层只发生在批量窗口或压缩事务内。
2. **分总层 root-only**：每树一条 ≤150 token 画像 + 0–100 helpfulness 闸；不建多层总述。
3. **总述视图必须带句柄**：`[Data: Node(#), Msg(#), +more]`，且不回写路由视图（01 §8.2）。
4. **树必须保留压平检索旁路**：ReadAgent/MemWalker 反证 + RAPTOR collapsed-tree 结论双向支持。
5. **叶层原文永不进摘要字段**：节点只存 `page_span` 与句柄，原文 append-only；这正是 ReadAgent 与 bgx666 `details` 的共同点。
6. **"流动"的缓存代价必须自测**：三篇 0 篇做过，别把推断当结论。
